## 1. 為什麼要做這件事（Why）

### 1.1 現況痛點

目前 PyVRP 是一個**純 Python 套件**，使用者必須具備下列能力才能使用：

| 痛點 | 影響對象 | 嚴重程度 |
|------|----------|----------|
| 必須手寫 Python 程式呼叫 `Model` API | 業務人員、非工程師 | ★★★★★ |
| 必須先把 WGS84 經緯度轉成平面座標再輸入 | 所有使用者 | ★★★★☆ |
| 求解結果是一堆 `Route` 物件，無圖形化呈現 | 所有使用者 | ★★★★☆ |
| 想驗證演算法效果就得每次寫 plotting 程式碼 | 研究人員 | ★★★☆☆ |
| 無法即時調整參數對比結果 | 研究人員、教學用 | ★★★☆☆ |

### 1.2 商業價值

物流、配送、教學示範等情境，**真正需要 VRP 求解能力的人通常不是工程師**。
若能提供「填表單 → 點按鈕 → 看地圖」的零程式碼操作流程，PyVRP 的可用人群將從「Python 開發者」擴大到「物流規劃師、教師、學生、決策者」。

### 1.3 學術價值

本課程為「仿生計算（Bio-inspired Computing）」，PyVRP 內部使用的 **HGS（Hybrid Genetic Search）** 正是仿生演算法的代表作之一。透過視覺化前端，可以直接呈現 GA 在解空間中收斂的過程，讓修課同學「看得到」演算法在工作。

### 2.2 新增能力（Capabilities）

本次變更會引入 **4 個新 capability**：

| Capability | 中文名稱 | 簡述 |
|------------|----------|------|
| `vrp-input-form` | VRP 輸入表單 | 前端互動式表單，收集倉庫/店面/時間窗/車隊 |
| `vrp-rest-api` | VRP REST API | 後端 HTTP 介面，定義 `/api/solve` 等端點 |
| `vrp-solver-adapter` | VRP 求解器轉接層 | WGS84↔UTM 轉換 + PyVRP `Model` 整合 |
| `route-map-view` | 路線地圖視覺化 | Leaflet 地圖渲染倉庫、店面、多色路線 |

### 2.3 不在範圍內（Out of Scope）

下列項目**本次不做**，避免範圍蔓延：

- ❌ 多倉庫支援（PyVRP v0.5.0 本身不支援）
- ❌ 使用者帳號系統與權限管理
- ❌ 求解結果歷史紀錄與比較
- ❌ 支援 Solomon / VRPLIB 檔案匯入（後續可加）
- ❌ 即時收斂動畫（GA 過程視覺化，列為 stretch goal）
- ❌ 行動裝置完整 RWD（先以桌面 1920×1080 為主）
- ❌ 部署到雲端（先在本機 `localhost` 跑通即可）

## 3. 為何採取這個方案（Why this approach）

### 3.1 技術選型理由

| 層 | 選擇 | 原因 |
|----|------|------|
| **前端框架** | **無框架**（Vanilla JS + HTML + CSS） | 課程作業規模，避免 webpack/npm 等重型工具鏈；檔案數最少、零建置流程 |
| **地圖套件** | Leaflet.js | 開源、免 API key、文件齊全、需求書直接建議 |
| **後端框架** | FastAPI | Python 原生、自動產生 OpenAPI 文件、type hints 友善 |
| **座標轉換** | pyproj | Python 地理運算事實標準，PyVRP 文件亦推薦 |
| **求解核心** | PyVRP `Model` 高層 API | 不直接操作 C++ 層，降低耦合 |
| **資料交換格式** | JSON | 前後端共通，無需額外序列化函式庫 |

### 3.2 架構決策摘要

> 詳細決策與替代方案討論請見 `design.md`

1. **前後端分離**：前端純靜態，可直接用 `python -m http.server` 或 FastAPI 的 `StaticFiles` 掛載
2. **同步求解**：v1 採同步阻塞 API，求解完成才回應；非同步任務佇列留待 v2
3. **單檔上傳 vs 表單輸入**：兩者並存，但 **v1 先做表單**，檔案上傳列入後續迭代
4. **整數比例尺**：UTM 公尺值乘以 10 取整，保留一位小數精度，避免 PyVRP 整數化的精度損失

## 4. 影響評估（Impact）

### 4.1 影響的程式碼

| 路徑 | 變動類型 | 說明 |
|------|----------|------|
| `pyvrp/` | **不動** | 不修改 PyVRP 核心，僅當函式庫使用 |
| `webapp/backend/` | 新增 | FastAPI 應用主體 |
| `webapp/frontend/` | 新增 | HTML/CSS/JS 靜態檔 |
| `pyproject.toml` | 修改 | 新增 `fastapi`、`pyproj`、`uvicorn` 依賴 |
| `README.md` | 修改 | 新增「Web Interface」啟動章節 |

### 4.2 風險與緩解

| 風險 | 機率 | 緩解措施 |
|------|------|----------|
| 經緯度範圍跨 UTM 帶（如台灣東西橫跨 50/51 帶） | 低 | v1 限制單一 UTM 帶；偵測到跨帶時前端報錯 |
| 大量店面（>500）導致前端卡頓 | 中 | 使用 Leaflet `markercluster` 外掛分群 |
| PyVRP 求解時間過長使前端 timeout | 中 | 設定合理 `max_runtime`（預設 10 秒）；前端顯示 loading |
| 使用者輸入時間窗不合理（早 > 晚） | 高 | 前端表單即時驗證 + 後端 422 錯誤回應 |

## 5. 成功標準（Acceptance Criteria）

本次變更完成的定義：

- ✅ 使用者打開 `http://localhost:8000` 即可看到表單頁面
- ✅ 可新增 1 個倉庫 + ≥3 個店面 + ≥2 種車型
- ✅ 點擊「開始計算」後 10 秒內回傳結果（10 個店面以內）
- ✅ 地圖正確顯示所有地點與多色路線軌跡
- ✅ 路線詳細資訊面板顯示每台車的順序、距離、抵達時間、總載重
- ✅ 後端 `/docs` 自動產生 OpenAPI 互動文件
- ✅ 提供 1 份 README，說明如何啟動前後端
- ✅ 提供 1 份示範資料（如台北市 10 家便利商店的經緯度）可一鍵載入

## 6. 後續延伸（Future Work）

完成此次變更後，可繼續推進：

1. **GA 收斂動畫**：透過 WebSocket 推送每代最佳解，前端動畫呈現
2. **VRPLIB 檔案匯入**：支援標準 benchmark 格式
3. **多解比較**：同時跑多個 seed，並排比較
4. **參數調校面板**：在前端開放 `PopulationParams`、`PenaltyParams` 微調
5. **匯出 PDF / PNG 報告**：地圖與路線明細打包下載
6. **多倉庫支援**：等 PyVRP 上游加入多倉庫後同步開發
