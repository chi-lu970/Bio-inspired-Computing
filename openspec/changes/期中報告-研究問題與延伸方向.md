# 期中報告：研究問題整理與延伸方向

> 基於論文：*PyVRP: A High-Performance VRP Solver Package*（Wouda, Lan, Kool, 2024）

---

## 一、作者在研究什麼問題？

### 核心問題

> **如何設計一個既高效、又容易使用和擴充的 VRP 求解套件？**

這句話看起來簡單，但背後有三個獨立的難題同時要解決：

---

### 難題 1：VRP 本身是極難的最佳化問題

VRP 是 **NP-hard** 問題，意思是：問題規模一大，找到**絕對最優解**在計算上幾乎不可能。

- 10 個城市有 10! ≈ 360 萬種排列
- 100 個城市，暴力搜尋根本算不完
- 加上容量限制、時間窗，難度更高

所以學術界的策略是：不追求最優，而是在合理時間內找到**夠好的解**（啟發式演算法）。

**作者解法：** 採用 HGS（混合遺傳搜尋），結合遺傳演算法的廣域探索與局部搜尋的精準改善。

---

### 難題 2：效能 vs 可用性的取捨

過去的高效 VRP 求解器（如 HGS-CVRP）幾乎全用 C++ 寫死，使用者沒辦法改任何東西。
但純 Python 實作又太慢，無法達到競賽等級的效能。

**作者解法：** 精確找出「效能瓶頸」只佔程式碼的一小部分，其餘交給 Python。

```
局部搜尋操作（佔執行時間 80–90%）→ C++ 實作
GA 主迴圈、種群管理、交叉算子    → Python 實作（可自訂）
```

結果：使用者可以用 Python 插拔演算法的每個模組，效能損失極小。

---

### 難題 3：動態平衡「探索」與「可行性」

遺傳演算法容易收斂到局部最佳解（種群同質化），但如果強迫每個解都可行，又會限制搜尋空間。

**作者解法：** 三個機制聯動解決這個問題：

| 機制 | 解決的問題 |
|------|----------|
| 雙子群（可行 + 不可行） | 不可行解也保留，擴大搜尋空間 |
| 動態懲罰（自動調整罰分） | 維持 43% 解可行，自動平衡 |
| 多樣性指標（BPD）+ 競賽選擇 | 防止種群退化成一模一樣的解 |

---

### 作者解決了什麼？

| 解決的問題 | 具體成果 |
|----------|---------|
| VRP 求解效能 | 贏得 2021 DIMACS VRPTW 競賽第一名、NeurIPS 2022 VRP 競賽第一名 |
| 通用性 | 同時支援 CVRP 和 VRPTW，架構可延伸到其他 VRP 變型 |
| 易用性 | `pip install pyvrp` 即可用，5 行程式碼建模求解 |
| 開放性 | MIT 授權、完整文件、單元測試，歡迎社群貢獻 |
| 可再現性 | 論文程式碼完整公開，實驗可重現 |
| ML 研究橋樑 | 讓機器學習研究者能直接在頂尖 VRP 解上做延伸 |

---

### 作者還沒解決什麼？（論文中的限制）

1. **僅支援 CVRP 和 VRPTW**，更複雜的變型（多倉庫、異質車隊、隨機需求）需社群擴充
2. **最小化距離為主**，車輛數最小化需要在外層包裝邏輯
3. **整數距離為主**，浮點數精度模式需手動編譯
4. **無動態/即時 VRP 支援**（訂單即時進來的場景）

## 二、你可以做哪些延伸方向？

以下依「難度」與「生活相關度」分類，每個方向都說明：是什麼問題、對應什麼生活場景、你可以怎麼做。

---

### 方向 A：從 VRP 簡化到 TSP，實作純 Python GA ⭐ 推薦入門

**是什麼：** TSP（旅行推銷員問題）是 VRP 的最簡單特例，只有一個人、沒有容量限制，找最短的環形路徑。

**生活場景：** 外送員一個人送完今天所有訂單，怎麼排路線最省時？

**你可以做：**
- 用純 Python 實作遺傳演算法解 TSP
- 對比「加入 2-OPT 局部搜尋」vs「不加」的效果差異
- 畫出種群多樣性 vs 迭代次數的收斂圖
- 對照 HGS 的設計，說明哪些機制可以從 VRP 移植到 TSP

**和論文的連結：**
- 對應 HGS 的局部搜尋（2-OPT 是 PyVRP 11 種操作之一）
- 對應種群多樣性管理的概念

---

### 方向 B：校園外送路線最佳化 ⭐ 實際且有趣

**是什麼：** 在學校或宿舍區，外送平台派幾個外送員同時接多張訂單，怎麼分配才能讓所有人等最短時間？

**生活場景：** Uber Eats、Foodpanda 在校園內的派單邏輯。

**真實的限制：**
- 每個外送員有最大承載量（例如最多帶 3 份餐）
- 餐點有保溫時限（時間窗：15 分鐘內送達）
- 出發點是餐廳，不是固定倉庫

**你可以做：**
- 用 PyVRP 的 VRPTW 建模這個問題（餐廳=倉庫、訂單=客戶、外送員=車輛）
- 自己產生測試資料（用學校地圖的座標）
- 用 GA（純 Python）和 PyVRP（HGS）各解一次，比較解的品質和時間
- 報告中討論：時間窗嚴格度如何影響解的難度

---

### 方向 C：台灣便利超商補貨路線 ⭐⭐ 有數據可用

**是什麼：** 統一、全家的配送中心每天要對幾百間門市補貨，貨車有載重限制、門市有收貨時間窗（早上某個時段）。

**生活場景：** 你每天早上去 7-11 買早餐，架上的貨是怎麼補上來的？背後就是 VRPTW。

**為什麼適合：**
- 台灣便利超商密度世界第一（每平方公里最高），是很好的 VRP 案例
- 可以用公開的地址資料自行建模
- 補貨時間窗（例如早上 6–9 點限制收貨）是現實的時間窗

**你可以做：**
- 用 PyVRP 建模一個簡化版（例如台北市 30 間門市 + 3 台貨車）
- 探討：如果延長/縮短時間窗，路線總距離怎麼變化？
- 加入「優先補貨」的概念（熱門門市優先），對應 PyVRP 的 `prize` 屬性

---

### 方向 D：台北 YouBike 調度問題 ⭐⭐ 有趣的新問題

**是什麼：** YouBike 站點有的車太多、有的太少，需要派調度車把多的搬到少的地方，這是 **VRP 的一種（VRPP，Vehicle Routing with Pickup and Delivery）**。

**生活場景：** 你去租 YouBike，結果那站沒車，走去下一站才有。調度做不好就是這樣。

**有趣的點：**
- 每個站既是「取貨點」也可能是「送貨點」
- 調度車有容量限制（一次最多載幾台）
- 目標是最小化調度後各站不均衡的程度

**你可以做：**
- 簡化問題：把「借還數量不均衡」建成需求，PyVRP 或自寫 GA 求解
- 用真實的 YouBike 開放資料（政府 API 可取得各站即時車輛數）
- 比較不同時段（尖峰 vs 離峰）的調度策略

---

### 方向 E：醫療院所的行動醫療路線 ⭐⭐⭐ 有社會意義

**是什麼：** 偏鄉地區的行動醫療車，每週要去幾個村莊為老人健檢，車上醫護人員有限，每個村莊有特定可服務時間（例如只在上午）。

**生活場景：** 台灣山地原住民部落、離島醫療資源不足問題。

**對應的問題：**
- 醫療車容量 = 一次能服務幾人
- 時間窗 = 村莊可接受服務的時段
- 距離 = 山路行車時間（非直線距離）

**你可以做：**
- 設計一個假想情境（例如南投縣山地 20 個部落 + 2 台醫療車）
- 用 PyVRP 建模，輸出最佳路線
- 討論：如果多一台車，能多服務幾個部落？這個「邊際效益」值不值得增加成本？

---

### 方向 F：演算法本身的改進 ⭐⭐⭐ 適合想深入的人

**是什麼：** 在 PyVRP 框架內替換或改進某個模組，觀察效能變化。

**幾個具體方向：**

| 改進目標 | 做法 | 觀察指標 |
|----------|------|---------|
| 換一個交叉算子 | 用 OX（順序交叉）取代 SREX | 解質量、收斂速度 |
| 換一個多樣性指標 | 用漢明距離取代 BPD | 種群多樣性維持 |
| 改良停止條件 | 加入「連續 N 代無改善」 | 避免無謂等待 |
| 不同初始解策略 | 貪心初始解 vs 隨機初始解 | 收斂速度比較 |

**和論文的連結：** 論文 Section 4 明確說明這些都設計為可替換的模組，正是為了讓研究者做這種比較實驗。

---

## 三、建議你選哪個方向？

根據你的情況（仿生計算課、期中報告、純 Python GA）：

```
最推薦組合：方向 A + 方向 B 或 C

先做：方向 A（純 Python GA 解 TSP）
  └─ 這是你的「核心實作」，展示你理解了 GA

再做：方向 B 或 C（用 PyVRP 解實際問題）
  └─ 這是你的「延伸應用」，對比論文方法 vs 你的方法

報告結構建議：
  1. 問題介紹（VRP 是什麼，為什麼難）
  2. 論文方法回顧（HGS 演算法）
  3. 你的實作（純 Python GA 解 TSP/簡化 VRP）
  4. 實驗比較（你的 GA vs PyVRP HGS）
  5. 結論（GA 的優缺點，HGS 改進了什麼）
```

這樣的報告結構同時展示了：**理論理解（論文）+ 工程實作（程式）+ 實驗分析（比較）**，三個面向都有。
